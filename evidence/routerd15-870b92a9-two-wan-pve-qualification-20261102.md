# routerd 1.5 二重 WAN の PVE 実通信検証

## 結論

リビジョン `870b92a9eb4af24331937b12b7a1a2cc72bc95a6` の Linux 候補で、独立 VLAN のクライアント通信が優先 WAN-A を通りました。WAN-A の独立上流名前空間を停止すると、WAN-B へ切り替わりました。WAN-A を復旧すると、手動再適用なしで優先 WAN-A へ戻りました。

空の新規 1.5 設定へ置換すると、経路規則、経路表、変換とクライアント通信は消えました。同じ候補設定を再適用すると、通信は WAN-A で復旧しました。

これは Linux の `HealthCheck`、`EgressRoutePolicy`、`NAT44Rule`、明示した防火壁ゾーンの限定した実機検証です。IPv6 の経路選択、物理 WAN 障害、長時間の接続維持、ECMP、FreeBSD、および全機能の合格を示すものではありません。

候補は空の 1.5 状態領域から開始しました。LAN、二つの WAN、各 WAN の次ホップに対する TCP 健全性確認、優先経路選択、送信元変換、LAN 信頼ゾーンと WAN 非信頼ゾーンを明示しました。健全性確認の対象は WAN-A の `198.18.16.1:8080` と WAN-B の `198.18.18.1:8080` です。

## 観測結果

1. 初期状態は 13 資源で `Healthy` でした。規則優先度 `10110` と `10120`、経路表 `110` と `120`、各 WAN の既定経路が存在しました。
2. VM224 からの新規 HTTP 要求は 3 回とも本文 `A` を受信しました。WAN-A のパケット捕捉では、TCP 接続開始の送信元が `198.18.16.2`、宛先が `198.18.16.1:8080` でした。送信元変換と優先経路を確認しました。
3. VM220 の WAN-A 名前空間を停止すると、次の新規 HTTP 要求は本文 `B` を受信しました。WAN-B の捕捉では、送信元が `198.18.18.2`、宛先が `198.18.18.1:8080` でした。障害中の全体状態は、失われた `HealthCheck` を反映して `ERROR` でした。経路選択と転送は WAN-B で継続しました。
4. WAN-A 名前空間を再作成すると、次の新規 HTTP 要求は本文 `A` を受信しました。全体状態は `Healthy` へ戻り、WAN-A 捕捉の送信元は再び `198.18.16.2` でした。候補設定の再適用やルーター再起動は行っていません。
5. 空の新規 1.5 設定への `routerctl apply --replace` は世代 1 の `Healthy`、資源数 0 になりました。優先度 `10110` と `10120`、経路表 `110` と `120` は消え、VM224 の HTTP は 3 秒でタイムアウトしました。この置換は `3 orphaned managed artifacts found` の警告を返したため、警告が無いことは主張しません。観測対象の規則、経路、通信は撤回されました。
6. 候補設定の再適用は世代 2 の `Healthy`、13 資源となり、VM224 の新規 HTTP 要求は 3 回とも本文 `A` を受信しました。

切替時間の目標値は、この試験では設定していません。

## 復元

VM219 の元の `routerd`、`routerctl`、`routerd-healthcheck`、設定、状態領域、起動 ISO を復元しました。元の SHA-256 は順に `a1cbdd287e777d9eb090512ec7b7fb69f2340f0f12a71ed5567a8e2dcd2626f8`、`7de346416d215f842deaee95f615dad4c5bbb3c8d78f376d2a43ded55554b8f9`、`28c0b035ad9bce1c68a9480794a2d9d214287109fa7b741797138ab34363971f` と一致しました。`routerd` と `routerd-dnsmasq` はともに稼働状態です。

VM220 の二つの試験名前空間と HTTP プロセスを削除しました。VM224 は試験前と同じ停止状態へ戻しました。VM219 と VM220 の VLAN 設定から VLAN 3134 を除去し、候補 ISO と候補実行物を削除しました。
