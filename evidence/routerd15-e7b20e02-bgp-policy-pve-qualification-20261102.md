# routerd 1.5 BGP 接頭辞方針の PVE 実通信検証（2026-11-02）

## 結論

`e7b20e0233fca4c32a689d93ee2b13f8b2a38396` の Linux 配布物を PVE
VM219 で実行し、独立した VM220 の FRRouting `bgpd` と VLAN 3132 上で
eBGP を確立しました。VM220 が同時に広告した二つの接頭辞のうち、
`10.77.60.0/24` だけを VM219 のカーネル経路表へ導入しました。
`10.77.61.0/24` は導入されませんでした。

確立済みセッションを維持したまま、許可接頭辞を撤回すると導入経路が消えました。
同じ接頭辞を再広告すると、同じ次ホップと `proto bgp` で復帰しました。

## 観測結果

1. `BGPRouter/policy-edge` と `BGPPeer/policy-peer` は
   `Established` となり、確立ピア数は 1 でした。
2. VM220 の BGP 表には、VM219 から受信した `198.18.15.0/24` がありました。
3. VM220 が `10.77.60.0/24` と `10.77.61.0/24` を同時に広告した状態で、
   VM219 の経路表は次だけを表示しました。

   ```text
   10.77.60.0/24 via 198.18.16.1 dev rd15-wan proto bgp metric 200
   ```

4. `ip -4 route show exact 10.77.61.0/24` は空でした。VM219 の BGP 状態にも
   `10.77.61.0/24` はありませんでした。
5. VM220 で `10.77.60.0/24` の広告だけを撤回すると、セッションは
   `Established` のままでした。VM219 の許可経路は消え、BGP の転送経路数は
   0 になりました。拒否接頭辞も引き続きありませんでした。
6. VM220 が許可接頭辞を再広告すると、VM219 に同じ `proto bgp` 経路が復帰し、
   BGP の転送経路数は 1 に戻りました。拒否接頭辞は引き続きありませんでした。

## 設定上の防御

WAN からルーター自身への TCP/179 は、独立ピアの
`198.18.16.1/32` に限定した `FirewallRule` で許可しました。
静的判定は `action=accept` であり、適用済み nftables 規則も
`ip saddr 198.18.16.1 tcp dport 179` に限定されていました。

## 適用結果の扱い

`routerctl apply --replace` は、既存の試験基盤に残る `dnsmasq` と
`ServiceUnit` の不整合のため、`runtime-apply` を未確認として終了しました。
一方で、現行バイナリが読み込んだ新規設定から BGP デーモンの待受、ピア確立、
接頭辞方針、カーネル経路の導入・撤回・復帰は観測済みです。

したがって、この証跡は BGP の実通信方針検証を合格としますが、当該基盤での
`apply` 完了結果を合格とは扱いません。基盤の残留資源を含まない新規導入経路で
`apply` 完了を別途確認する必要があります。

## 復旧

試験後、VM219 の実行ファイル、設定、状態ディレクトリ、接続メディアを
試験前の値へ戻しました。`routerd` と `routerd-dnsmasq` は `active`、
`routerd-bgp` は `inactive` です。

VM220 の試験用名前空間、`bgpd` プロセス、VLAN インターフェースを削除しました。
VM219 に残った試験用 `10.77.60.0/24` 経路も個別に削除し、許可・拒否の両方の
対象経路がないことを確認しました。VM219 の接続メディアは
`routerd15-a23970a.iso`、VLAN トランクは `3131;3132;3133` へ戻しました。
