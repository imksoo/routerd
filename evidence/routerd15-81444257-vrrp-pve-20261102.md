# VRRP の三 VM PVE 実通信・引継ぎ・構成撤回・復旧

対象リビジョンは `81444257bd89a9f3f25ed9fd7e7f1023c6fa18c9` です。候補配布物の SHA-256 は
`a07047cfc3bc3fc9131fc2bbda7e052bc736f0e52cc1deb7229fafa5cdb039a7` でした。

VM219 と VM220 を候補、VLAN 3131 の VM224 を独立クライアントにしました。二候補は
`198.18.15.2/24` と `198.18.15.3/24`、VRRP 仮想 IP `198.18.15.1/32` を使用しました。
VRRP パケットを許可する LAN 防火壁ゾーンと既定防火壁方針を新規 1.5 構成へ明示しました。

1. 初期選出では VM219 だけが仮想 IP を保持し、VM224 の ICMP は 2/2 成功しました。
2. VM219 を停止すると VM220 が仮想 IP を取得しました。VM224 の ICMP は 3/3 成功しました。
3. VM219 の復帰後も VM220 が仮想 IP を維持し、VM219 は待機となりました。VM224 の ICMP は 2/2 成功しました。
4. 両候補へ空の新規 1.5 構成を `routerctl apply --replace -f` で適用すると、両方の資源数は 0 となり、仮想 IP と VM224 の ICMP は撤回されました。
5. 同じ `routerctl apply --replace -f` で各候補の VRRP 構成を再適用すると、両候補は `Healthy`、資源数 5 となりました。VM219 だけが仮想 IP を保持し、VM224 の ICMP は 2/2 成功しました。

最初の試行は LAN 防火壁ゾーンを含まない構成で、VRRP の内部許可規則もなく分裂主系となったため無効です。
また、初期化スクリプトを復旧へ混ぜた試行は VM219 の `ERROR` を生じたため無効です。上記は両方を除外した再試験です。

試験後は VM219、VM220、VM224 を試験前の状態へ戻しました。試験用 ISO、一時配置、スナップショットを削除し、VM219 と VM220 は稼働、VM224 は停止へ復元しました。

この記録は Linux の IPv4 VRRP と構成撤回・再適用を対象にします。物理 WAN 障害、既存 TCP 接続、DHCP リース継続、IPv6 VRRP、FreeBSD、および routerd 1.0 全機能の合格判定は対象外です。
