# DHCPv4 動的ゲートウェイ方針の三 VM PVE 実通信・撤回・復旧

対象リビジョンは `81444257bd89a9f3f25ed9fd7e7f1023c6fa18c9` です。候補配布物の SHA-256 は
`a07047cfc3bc3fc9131fc2bbda7e052bc736f0e52cc1deb7229fafa5cdb039a7` でした。

VM219 を候補、VLAN 3131 の VM224 を独立クライアント、VLAN 3132 の VM220 を独立 DHCPv4
サーバおよび HTTP 上流にしました。新規 1.5 構成は `DHCPv4Client` の状態を
`EgressRoutePolicy` の `gatewayFrom` として参照し、`gatewaySource: dhcpv4` を指定しました。

1. VM220 は `198.18.16.100/24`、既定ゲートウェイ `198.18.16.1`、DNS サーバ
   `198.18.16.1` を DHCPv4 で払い出しました。候補は `Healthy` となり、経路表 123 に
   `198.18.16.1` 経由の既定経路、優先度 10123 のマーク `0x122` 規則、NAT44 と
   `routerd_policy` の印付け規則を導入しました。
2. VM224 の新規 HTTP は VM219 を通り、VM220 の `192.0.2.1:18083` へ到達しました。
   VM220 の記録は変換後送信元 `198.18.16.100` を示しました。
3. `2026-11-02T12:56:25Z` に VM220 の DHCPv4 サーバだけを停止しました。リース失効後の
   `12:58:17Z`、候補は `PENDING` となり、WAN アドレス、WAN の既定経路、経路表 123 の
   既定経路は消えました。VM224 の新規 HTTP は接続不能でした。印付け規則と規則番号は
   残りましたが、転送先の経路はありませんでした。
4. VM220 の DHCPv4 サーバだけを再開すると、`12:58:30Z` の ACK で同じリースを再取得しました。
   `12:58:39Z` には候補が `Healthy` へ戻り、WAN アドレス、既定経路、経路表 123 が復帰しました。
   VM224 の新規 HTTP も再び VM220 へ到達しました。候補機の再起動は行っていません。

準備中に VM224 の起動待機コマンドの引用符が壊れ、クライアント設定の投入が一度失敗しました。
候補の DHCPv4 取得と実通信より前に安全なファイル転送方式で投入し直したため、この失敗は通信結果に
含めていません。

試験後は VM219、VM220、VM224 を試験前の状態へ戻しました。試験用 ISO、一時配置、
スナップショットを削除し、VM219 と VM220 は稼働、VM224 は停止へ復元しました。

この記録は DHCPv4 で得た IPv4 ゲートウェイを使う IPv4 方針経路を対象にします。異なる
ゲートウェイへの切替、送信元選択、VRRP、物理 WAN 障害、IPv6 動的ゲートウェイ、FreeBSD、
および routerd 1.0 全機能の合格判定は対象外です。
