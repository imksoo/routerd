# Linux HA 仮想アドレス PVE 分離 VLAN 試験

## 結論

`routerd v20261027.1620 (ea892a6b)` を VM219 と VM220 へ導入し、VM224 を独立クライアントとして VLAN 3154 に接続しました。VIP 通信、主系停止時の引継ぎ、停止した候補の再起動、構成撤回と再適用を確認しました。

## 実行対象

- パッケージ SHA-256: `505d386a29fa9d7506c3005389bf828d64689b011d7f0652643b5c0f160fc7a3`
- 実行バイナリ: `routerd v20261027.1620 (ea892a6b)`
- VM219: `172.18.0.2/16`、優先度 150
- VM220: `172.18.0.3/16`、優先度 100
- VM224: 独立クライアント、`172.18.1.250/16`
- 分離経路: `br-rd15-lab` の VLAN 3154
- 仮想アドレス: `172.18.0.1/32`、VRID 51、`preempt: false`

VLAN 3152 は VM221–223 が使用中と確認したため、試験対象から除外しました。

## 観測

1. VM220 が主系、VM219 が待機系となり、VM224 から VIP への ICMP は 3/3 応答しました。近隣解決は VM220 の MAC アドレスでした。
2. VM220 を強制停止すると、VM219 が主系となり VIP を保持しました。VM224 の 200 ミリ秒間隔 45 回の ICMP は 32 回応答し、停止後の連続 13 標本が欠落した後に復旧しました。この値は今回の観測値であり、切替時間の目標値ではありません。
3. VM220 を再起動すると、VM219 は主系、VM220 は待機系のままでした。これは `preempt: false` と一致し、VM224 からの ICMP は 3/3 応答しました。
4. 両候補へ空の新規 1.5 構成を適用すると、管理資源数は両方 0 となり、VIP と DHCP UDP 67 番待受が消えました。VM224 の ICMP は 0/2 でした。
5. 同じ新規 HA 構成を再適用すると、VM219 が主系、VM220 が待機系へ戻り、VIP と主系の DHCP UDP 67 番待受が復旧しました。VM224 の ICMP は 3/3 応答しました。

## 準備時の修正

最初の構成にはファイアウォールゾーンがなく、既定の入力遮断が VRRP 広告を `keepalived` へ渡さず、二重主系になりました。この試行は不合格として除外しました。LAN の `FirewallZone` と `FirewallPolicy` を追加した新規構成 `12ebfc4c` を適用後、VRRP の相互広告、単一主系、VIP 通信を確認してから本試験を実施しました。

## 範囲外

`RouterdCluster` のフェンシング、分断時の二重主系防止、DHCP リース同期、既存 TCP 接続、WAN/NAT/DNS/IPv6 の状態引継ぎ、長時間障害、物理回線、FreeBSD は未確認です。この結果は冗長化全体、Linux 全体、または置換可能品質の合格を意味しません。
