# BGP の PVE 独立ピア試験

実施日: 2026-11-02（JST）  
対象ソースリビジョン: `570606b7b727f35861816c6c0632c9bfecd04452`  
VM219 の `routerd` SHA-256: `a1cbdd287e777d9eb090512ec7b7fb69f2340f0f12a71ed5567a8e2dcd2626f8`  
VM219 の `routerd-bgp` SHA-256: `615e5b90d75c055ae43a12df0c4012b74ed5ab4a3f91bed8e295f93d4d858e99`

`8b80a174` から対象リビジョンまでの差分は設計資料と証跡だけです。したがって、
VM219 の実行バイナリが持つ BGP のソース上の振る舞いは対象リビジョンと同一です。

## 結果

VM219 と VM220 は VLAN 3132 上で eBGP セッションを Established にしました。
VM220 が配布した `198.18.50.0/24` は、VM219 のカーネル経路表へ
`proto bgp` として導入されました。VM220 側で配布を停止すると、セッションを
維持したまま VM219 の BGP 状態とカーネル経路表から当該経路が撤去されました。
配布を戻すと、同じ経路が再導入されました。

## 構成

- ルーター: VM219、`198.18.16.2`、AS 64520
- ピア: VM220、`198.18.16.1`、AS 64521、受動待受
- 接続: `br-rd15-lab` の VLAN 3132
- VM219 の資源: `BGPRouter/pve-bgp`、`BGPPeer/pve-peer`
- VM220 の資源: `BGPRouter/pve-bgp`、`BGPPeer/pve-router`
- 配布プレフィックス: VM220 の接続済み `198.18.50.0/24`

VM219 は routerd 1.5 の試験対象です。VM220 は別 VM・別プロセス・別バイナリの
ピアとして動かしました。VM220 の `routerd` SHA-256 は
`3f0307b7ce39fc84dc225f6dd508de8a322da1d1055341bad5dfcc3cc8d35e04`、
`routerd-bgp` SHA-256 は
`44b959d773b220813ce4ed5f833e6a655305db841122cab85ece3654cd2f9379` です。

## 観測

- VM219 の TCP/179 は `routerd-bgp` が `198.18.16.2:179` で待受
- 両側で peer 状態は `SESSION_STATE_ESTABLISHED`
- VM219 は peer から 1 prefix を受信し、`fibRoutes: 1` を記録
- VM219 のカーネル経路表は
  `198.18.50.0/24 via 198.18.16.1 dev rd15-wan proto bgp metric 200`
- この状態で VM219 から `198.18.50.1` への ICMP は 3/3 応答
- VM220 の接続済み経路配布を空にすると、セッションは Established のまま、
  VM219 は `fibRoutes: 0`、`installedNextHops: {}`、対象 prefix なしへ遷移
- 撤回後の `ip -4 route show exact 198.18.50.0/24` は空
- VM220 の配布設定を復元すると、VM219 に同じ `proto bgp` 経路が再導入

撤回確認で `ip route get 198.18.50.1` は使いません。BGP 経路がない場合でも、
既存の既定経路が同じ次ホップを返すためです。撤回・復帰の判定は、対象
プレフィックスの直接表示と routerd の FIB 状態で行いました。

## 復帰

両 VM の試験前の正本設定を SHA-256 で照合して再適用しました。VM219 は
21 資源、generation 38 の `Healthy` 状態へ戻しました。VM220 は 13 資源、
generation 55 の `Healthy` 状態へ戻し、試験用 `rd15-bgp-up` VLAN
インターフェースも削除しました。
