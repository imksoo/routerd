# routerd 1.5 Linux セキュリティ機能対照

## 結論

routerd 1.5 は、旧設定形式を読み込まず、新しい設定で同じ防御目的を明示します。
この表は PVE VM219 に保全した `router.yaml.legacy-e3b49db` を機能の根拠として使います。
旧設定、旧状態データベース、移行処理は導入手順にも実装にも使いません。

各行は、目的、1.5 の構成要素、独立 VLAN における受入試験を対応付けます。
「未検証」は機能がない意味ではなく、その構成での実通信証跡がまだない状態です。

| 旧構成の防御目的 | 1.5 の新規構成 | Linux 実通信の状態 | 残る受入試験 |
| --- | --- | --- | --- |
| WAN、LAN、管理網の分離と既定拒否 | `FirewallZone` の `untrust`、`trust`、`mgmt` と `FirewallPolicy` | 3 VLAN の PVE 試験で、LAN→管理網の明示許可と WAN→LAN の既定拒否を実測済み | ルーター自身への拒否、UDP、CIDR 選択、管理 CIDR |
| LAN から管理網への必要な到達だけを許可 | `FirewallRule/allow-lan-to-management` | HTTP は到達し、規則撤回後は遮断、再投入後は復旧 | プロトコル・CIDR 限定、既存通信の扱い |
| 旧 LAN セグメントから通常 LAN への限定許可 | `FirewallRule/allow-legacy-172-to-lan` | VLAN 3131 から VLAN 3132 へ、許可した送信元・宛先 CIDR と TCP ポートだけを到達させ、非許可送信元は遮断。規則撤回後は許可元も遮断し、再適用後に許可元だけ復旧 | 別の宛先 CIDR・ポート、UDP、既存通信の扱い |
| WAN から LAN、ルーター自身への不要な到達を拒否 | `FirewallZone/wan` と既定 `FirewallPolicy` | 独立 WAN クライアントから LAN HTTP への TCP は遮断され、`wan_to_lan` の拒否カウンターを確認 | ルーター自身への拒否、UDP、設定撤回後の既存通信 |

| 私設網宛の不用意な外部転送を防止 | `IPv4Route/private-10-blackhole` と `EgressRoutePolicy` の除外 CIDR | 静的黒穴経路と `EgressRoutePolicy` の除外 CIDRを、VLAN 3131 から VLAN 3132 への実通信、撤回、再適用で確認済み | 他の私設 CIDR、既存通信の扱い |
| 防火壁の拒否と通信記録を監査可能にする | `FirewallEventLog/default`、`TrafficFlowLog/default`、`LogSink` | 未検証 | 許可・拒否の記録、対象識別、設定撤回後の停止 |

## 試験の共通条件

受入試験は PVE の未使用 VLAN と独立 VM を使います。候補ルーター、LAN クライアント、
WAN または管理網の端点を別 VM または別 VLAN に置きます。各試験で、正常通信、
規則または上流の撤回、期待する遮断、再投入後の復旧を順に観測します。

候補試験後は VM219、VM220、VM224 の実行物、設定、状態、起動状態を元へ戻します。
この復元は試験成功の代替ではなく、隔離試験の終了条件です。

## 私設 IPv4 宛て黒穴経路の実通信記録

`e83b639b` の候補では、VLAN 3131 の VM224 を `198.18.91.10/24`、VLAN 3132 の
VM220 を上流ゲートウェイ `198.18.92.2/24` としました。候補は通常の既定経路と
`blackhole 10.0.0.0/8` を同時に適用しました。

VM224 から `10.23.45.67` への ICMP 要求 3 回はすべて失敗し、VM220 の捕捉は待受のままでした。
黒穴経路を除く厳密置換後、候補の経路検索は上流ゲートウェイを返し、同じ ICMP 要求 1 回を
VM220 が捕捉しました。黒穴経路の再適用後は要求が再び失敗し、上流捕捉は待受のままでした。
この記録は静的な黒穴経路を対象とします。`EgressRoutePolicy` の除外 CIDR は次の記録で確認しました。

## EgressRoutePolicy 除外 CIDR の実通信記録

空の 1.5 状態領域から候補を起動し、VLAN 3131 の VM224 を `198.18.91.10/24`、
VLAN 3132 の VM220 を `198.18.92.2/24` としました。`EgressRoutePolicy` は
`198.18.91.0/24` 発の既定宛先に印 `0x100` を付け、経路表 100 の上流経路を選びます。
`10.0.0.0/8` は除外し、主経路表の黒穴既定経路へ残しました。

通常宛先 `203.0.113.9` の ICMP 要求は、候補 WAN 側と VM220 で捕捉しました。
除外した `10.23.45.67` 宛ては、両方で未捕捉でした。除外 CIDR を外すと、同じ私設宛て
要求は候補 WAN 側と VM220 で捕捉されました。除外 CIDR の再適用後は再び未捕捉でした。
初回は前回候補の規則と経路表を残しており、所有権保護が外来資源として拒否しました。
候補停止中にそれらを削除し、空の状態から再試験した結果だけをこの記録に含めます。

## LocalServiceRedirect の UDP 実通信記録

`019ca029` の候補実行物を VM219 に一時導入しました。VLAN 3131 の VM224 は
`198.18.91.10/24`、候補の LAN 側は `198.18.91.1/24` とし、公開側を模した
`198.18.93.53:53` と `198.18.93.123:123` への経路だけを候補へ向けました。

候補は UDP 53 をローカル UDP 1053、UDP 123 をローカル UDP 1123 へ変換しました。
VM224 の `dig @198.18.93.53 redirect.test A` は `198.18.91.42` を返しました。
NTP 要求は 48 バイトの応答を受け、応答種別 4 と識別子 `RD15` を確認しました。
二つの nftables 規則は、各 1 パケットを記録しました。

`LocalServiceRedirect` を含まない設定への厳密置換は Healthy でした。規則の撤回後、
DNS は到達不能、NTP は 2 秒でタイムアウトしました。規則を再投入すると、同じ DNS
応答と NTP 応答が復旧し、各規則のパケット数は再び 1 になりました。既存の通信を
撤回時にどう扱うかは、この UDP 要求応答試験では未確認です。
