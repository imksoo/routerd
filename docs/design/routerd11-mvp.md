# routerd 1.1 MVPと開発行動原則

2026年11月7日。routerd 1.0を起点として、管理者一人が運用する homert、k8s-rt、pve-rt、Cloud SAMに必要なものへ絞り、実機で使える状態を改善する。1.5・2.0での作り直しを続ける計画にはしない。

2026年11月9日の所有者指示: routerdはコンフィグをレンダーして設定し、設定された対象の差異を修復し、設定から削除された対象は撤去する。関係ない別の設定は、同じホストやインターフェース上の手動追加を含めて残す。作成元や所有権の判定・記録は不要で、データベースとの互換性を理由に残さない。DHCPリースやSAMの動作に必要な状態は保持する。以下の設定外の余剰を一律に削除する記述より、この指示を優先する。

本書の最優先条件は、実機で問題を解決すること、コンフィグでマシンを管理すること、不要な製品コード・設定・テストを取り除くことである。開発担当はルートの [AGENTS.md](../../AGENTS.md) に従う。過去文書のテスト先行、模擬環境、全機能維持、全面検証などの条件が本書と衝突する場合、この1.1方針へ置き換える。

WireGuardのpeer集合とVXLANの転送先集合は、所有者の後続指示により現在のコンフィグどおりに管理する。設定前の集合は保持しない。

## 1 何を完成させるか

対象の4系統で使用する既存の設定と必要な通信を維持しながら、次を実現する。

1. 同じ設定をapplyすれば、設定された対象の手動変更・削除を設定どおりに戻す。関係ない別の設定は変更しない。
2. 初期導入時に、人が指定した物理NICと静的IPv4/IPv6アドレスを設定候補として取り込める。
3. 再適用、daemon/helper再起動、OS再起動、上流断と復帰の後も、設定に従って動作を再開する。
4. 4系統で使用しない機能と、それだけのためのコード・設定・テスト・依存を削除する。
5. 小さな変更を早く実機へ入れ、実際の通信結果を次の改修へつなげる。

利用者は一人である。不特定の利用者、存在を確認していない旧版、将来使うかもしれない機能のために実装や互換層を残さない。

## 2 残す範囲と削除する範囲

残す範囲は、homert、k8s-rt、pve-rt、Cloud SAMの実設定と、その設定を動作・復旧・撤去させる依存実装から決める。静的YAMLだけでなく、参照、when、動的に取得・生成する設定、実際に使う運用コマンド、helper、OSとの接続をたどる。importは今回明示された新機能として含める。

| 判断対象 | 方針 |
| --- | --- |
| 4系統で使う設定・動作 | 記法、既定値、参照と必要な意味を維持する |
| その動作に必要な共通処理・動的生成・更新・復旧・撤去 | 必要な最小実装を残す |
| 上記から使われない機能、Kind、フィールド、API、CLI、helper、backend | 削除する |
| 削除機能だけのschema、examples、文書、テスト、fixtures、CI、依存ライブラリ | 本体と一緒に削除する |
| OS・architecture・クラウド事業者の対応 | この4系統で実際に必要なものに限定する |
| 単に過去の例・試験profile・設計文書に登場するもの | それだけでは保持理由にしない |

削除を無効化フラグや別runtimeの追加で代用しない。共通packageの一部が必要なら、未使用部分を削る。現在の設定に直接書かれていないという理由だけで、DHCP更新、PDのprefix変更、BGP経路生成、SAMの役割変更などを誤って消さない。

互換対象は全1.0機能ではなく、この4系統の使用設定である。使っていない公開APIや旧イベント形式の維持義務は設けない。使用中のstatus参照とwhenの意味は保持する。旧managed:false、owner:external等は、実設定で使用している箇所と必要な作用を確認して整理し、全面管理と無関係な一般的共存モードを増設しない。

## 3 コンフィグがマシンを管理する

routerdが適用する設定は、保存されたコンフィグを宣言元とする。CLI・APIからの永続的な設定変更も同じ設定へ反映する。生成ファイルや実機の変更を勝手にコンフィグへ逆輸入しない。コンフィグ自身を編集してapplyすることは正規の設定変更である。

applyは明示設定と、その設定で有効になった機能の現在有効な動的結果に基づき、不足を作り、相違を直す。設定から削除した対象は撤去し、関係ない別の設定には触れない。

| 実機の状態 | applyの動作 |
| --- | --- |
| 設定されたアドレス・経路・仮想IFが消されている | 必要な状態を復元する |
| MTU、IF所属、Bridge member、経路属性などが変更されている | 設定の値・集合へ戻す |
| 関係ない別のアドレス・経路・rule・仮想IF・memberが追加されている | 変更しない |
| 生成ファイルが編集・削除されている | コンフィグから再生成して反映する |
| ファイルは正しいがkernelやサービスがずれている | 実体を再設定する |
| 設定から機能が削除されている | 再生成元を止め、不要な実体と生成物を撤去する |
| 希望する状態がすでに存在する | 過去の作成者を問わず利用する |
| 所有台帳・以前の適用記録がない | それだけを理由に拒否せず、設定と実体から処理する |

設定された対象は実体を確認し、不足や相違を修復する。config hash、生成内容hash、以前のApplied表示だけで現在の一致を判定しない。所有権や作成履歴の判定は行わない。

DHCP/PDの有効な取得値、BGPの選択経路、VRRP/SAMの役割に伴うVIPや経路は、設定に従う動的状態である。直結経路は正当なアドレスから導かれる。protocolの名前だけで任意の経路を残す扱いはしない。期限や猶予が必要な旧prefix等は、その機能の規則に従って保持・撤去する。

物理NICそのものやloopbackの存在と、そこで設定するアドレス・MTU・所属・管理状態を区別する。ARP/ND、conntrack、DNS cacheなど通信中のデータを毎applyで全消去しない。それらの機能・制限・期限を設定で管理する。「すべてをコンフィグで管理する」を、通信中の全レコードの静的列挙へ置き換えない。

## 4 既存設定の取り込み

routerctl importを追加する。既存ホストを読んで、1.1で使用するYAMLの候補を出す。通常の実行でネットワークを書き換えず、以後のplan/applyへ渡す。以下は実装するCLI案である。

~~~sh
routerctl import --interface enp1s0 --address 192.0.2.1/24 > imported.yaml
# imported.yamlを既存の完全なrouter.yamlへ統合してから適用する
routerctl plan -f router.yaml --replace
routerctl apply -f router.yaml --replace
~~~

NICを指定した部分取り込みを、マシン全体の完成した設定としてそのままapplyしない。既存のサービス・動的機能・他のNIC等を含む設定へ統合する。初回導入でも、管理するマシン全体の必要な設定を揃えてから全面管理へ移す。

取り込みは人が必要と判断して実行する初期導入の補助である。指定した物理NICと、明示的に選択した静的IPv4/IPv6アドレスだけを設定候補にする。既存設定に同じNICやアドレスの定義があれば、名前と参照を再利用する。

DHCP、SLAAC、PD、PPPoE、BGP、SAM等の現在値を静的設定に変換しない。経路、DNS、MTU、取得方式なども、ホストの既存状態から自動変換しない。必要な設定は人がコンフィグに記述する。

静的IPv6アドレスは現行schemaで表現する。既存環境の再現や、任意のネットワークダンプを変換する汎用import基盤は作らない。

旧管理元によるDHCP・RA・経路の再生成とrouterdが競合しないよう、対象環境の引き継ぎも実装する。物理NICの再作成や理由のない再接続を行わず、管理接続と実通信を確認する。無瞬断を、実機で確認せず保証しない。

importは初回導入や移管の入口であり、毎回applyの前に所有登録を要求する仕組みにはしない。

## 5 1.0を改善する実装方針

起点はimksoo/routerdの1.0 main。調査基準はe3b49dbb69c7de97bab9595884745eb7cbe93d92である。1.5/2.0のコードは、必要な改善を理解して選ぶ際の参考とする。ブランチ全体の取り込みや試作runtimeの併存を行わない。

- 外部入力を境界で型へ変換し、内部では具体型を使う。any、型判定、map/string往復を必要性なく多用しない。
- YAMLやJSONへ書き出して読み直す内部コピー、同じ値の再読込・再解析・再変換を減らす。
- 現在状態の担当を明確にし、複数の可変な正本や重複判断を減らす。
- Healthによる選択、経路・nftablesへの適用、成功結果の公開という順序を揃える。
- planは観測と判断を行い、通常の設定変更を起こさない。planのためのDB複製も、必要な範囲から減らす。
- OS操作やhelperの失敗を握り潰さず、何が変わり、何が未完了かを報告して再試行する。
- 置き換えた処理と不要な引数・fallback・互換経路を同じ変更で削る。
- 汎用リソースエンジン、独自フレームワーク、試験用の本体差し替え口を簡素化のために増やさない。

所有証明の整理は、使用する機能にある拒否処理から進める。SAM proxy_arp、Tunnel/VXLAN、helper監督、生成ファイル、MSSなどで見つかった過剰な制約を、必要な実動作と分けて取り除く。不要機能であれば、その機能ごと削除する。

DHCP/PDのリースと期限、enrollmentの識別情報、HA/SAMの役割・排他、必要な撤去対象など、実際の継続動作に必要な状態は残す。作成証明の撤去を理由に全状態DBを初期化しない。DB全面刷新を最初の実機投入の前提にしない。

## 6 配布と通常運用

対象で使用するパッケージ管理方式で導入・更新できるようにする。従来要望のapt/pkg化も対象OSに応じて実施する。現行の依存パッケージ導入と、routerd自身のdeb/pkg配布を混同しない。最初の実機投入は、既存のビルド・導入経路で進めてよい。

使用中の設定、鍵・資格情報の参照、必要なリース・状態を維持して更新する。設定済みホストは起動後に必要なサービスを開始し、helper停止や上流の断・復帰から回復する。過去の失敗ラッチや一件の不正記録で、関係のない機能まで止まり続ける状態を直す。ただしSAMの不正な適用履歴は、所有者の後続指示に従ってエラーを返し、処理を止める。

CLI/API、status、ログ、doctor等は実際に使う運用入口を残す。表示には実機で観測した状態と未完了の理由を出す。機能を使っていない場合は、診断画面やメトリクスの存在だけを保存理由にしない。

小さいOS基盤の要望を踏まえ、不要なhelperやパッケージを導入しない。専用ディストリビューション、全OS同等対応、50MB等の新しいサイズ目標を1.1の実機投入条件へ加えない。

## 7 強制する開発行動原則

以下は努力目標ではなく、作業の禁止・許可を定める規則である。

### 実機へ進む

変更は小さく作り、必要なビルド・設定読込み・実コマンドの確認後、対象の実環境と実相手機器で通信させる。全面監査、型整理の全完了、全テスト通過、coverage、全OS・全クラウドの組合せ確認を先に終える手順は禁止する。

検証先はhomert、k8s-rt、pve-rt、Cloud SAMとその実際の相手機器である。そこに含まれるPVE VMやクラウドVMは実際の導入先として扱う。実機の代わりに新しいテストVM群、netns harness、模擬ネットワークを作らない。

### 不要なテストと模擬環境を禁止する

mock、fake、シミュレーターによる振る舞いの代用を原則禁止する。実装をなぞっただけの期待値、自明な恒等式、固定した成功値、モックに仕込んだ応答を確認するだけのテストを禁止する。

このような作業は、成果に数えないだけでなく、時間と開発行為を浪費した方針違反としてマイナス評価・是正の対象にする。すでに存在する同種のテストにも適用し、専用fixtures、adapter、試験用抽象化、CI作業を含めて除去する。既存テストを緑にすることだけを目的とする修理は禁止する。

### 契約テストも事前に説明する

新規テストコードと既存テストの増補は、特定のテストについて事前に利用者の明示的な了承を得た場合だけ認める。インターフェースや呼び出し規約を守るテストでも自動的な例外にはしない。

説明には、守る契約と検出する具体的な誤り、コンパイラや実機確認で足りない理由、作成・維持の工数を含める。「回帰防止」「品質」「ベストプラクティス」だけでは理由にならない。テストの了承を、模擬環境を作る了承へ拡張しない。

### 根拠のない時間制限を禁止する

要求・プロトコル・確認された問題に基づかないテストのタイムアウトや経過時間アサーションを禁止する。10秒と決めたために12秒の正常完了を失敗とすることは認めない。その差を切り詰める必要性を説明できない既存テストも削除・修正する。

無限待ち防止の監視上限は、製品の合否条件と分ける。長く戻らない場合は進行状態とログを調べ、どこで止まったかを確認する。10分は異常を疑う例であり、一律の新タイムアウトではない。実プロトコルの期限・lease・再接続timerまで削る指示ではない。

### 計画から逸脱しない

着手前、引き継ぎ後、commit前にAGENTS.mdと現在のMVPを読む。着手時には今回変える箇所と実機で確認する内容を短く示す。許可済みの範囲内では自律して進める。禁止事項の例外、機能・試験・仕組みの追加、対象範囲の変更を独断で決めない。

違反を見つけたら、その変更と不要になった依存を除去し、何に時間を浪費したかを簡潔に報告して、本来の作業へ戻る。自己正当化や大きな再発防止フレームワークの作成へ進まない。

### 成果を保全し後片付けする

小さな実用的変更をcommit・pushし、差分、revision、実際に確認したこと、未確認事項を報告する。無関係なCI待ちで作業を止めない。実行していない実機確認を実施済みと書かない。

生ログ、pcap、dump、エビデンス、試行ごとの証跡は原則としてGitの追跡外に置く。必要な結果だけを短くcommitし、公開できたら作業用の生データ・一時ファイルを削除する。誤って追跡した不要証跡も現ツリーから除去する。

一区切りごとに、その作業で使ったbuild/test cache、download・展開cache、一時環境を整理・削除する。ソース、稼働設定、秘密、未公開の成果物、他の進行中作業のデータと混同しない。消せなかったものは対象と理由を報告し、放置しない。

## 8 コミット時の規約確認

このリポジトリのcommit-msg hookは、次の具体的な説明がないcommitを拒否する。

~~~text
Rule-Check: 今回の差分が、適用される行動規約にどう従っているか。
Scope-Check: 追加が必要な理由と、不要なものを勝手に増やしていない根拠。
Validation: 実際の確認と結果。実機未確認ならその内容を明示する。
Cleanup: 削除済みのログ・証跡・cache、または公開後に消す具体的な作業用データ。
~~~

OK、確認済み、問題なし、なし、未実施など一語だけの回答は説明として認めない。hookはAGENTS.mdを表示して再読を促し、メッセージに「AGENTS.mdを読み直せ。」を残す。

各cloneで次を設定する。

~~~sh
git config --local core.hooksPath .githooks
~~~

hookを無効化・迂回しない。GitHub API等から作るcommitにも同じ説明を付ける。hookは説明の存在を確認できても、内容の正しさまでは証明しない。実際の差分と照合し、禁止された変更があれば採用しない。AIが編集できるrepo内hookだけを、改変不能な強制境界とは扱わない。

強制力が必要な操作は、AIが変更できない管理設定・OS権限・受け入れ側で制限する。使用する開発ツールの既存機能を必要最小限で使い、新たな検査フレームワークやCI基盤を作る根拠にしない。テストの新規作成・増補を止める制限で、禁止対象の既存テストの削除まで妨げない。制限の整備を小さな改修や実機投入の開始条件にしない。

今回作成するrepo内hookと、管理者側の強制設定は別である。この変更で外部の管理設定やサーバー側の受け入れ制限まで導入済みとはしない。

## 9 実施順序と完成条件

| 区切り | 残す成果物と実機確認 |
| --- | --- |
| 最初の実機投入 | 4系統の使用設定を押さえ、1.0起点のbuildと小さな改修を実際の対象へ入れて通信を確認する |
| 設定への復元 | 使用中の機能から、設定された対象の手動変更・削除・生成ファイルの変更をapplyで戻す |
| 取り込みと移管 | 人が選択した実対象のNIC・静的IPv4/IPv6アドレスをimportし、必要な設定を人が補って通常applyへつなぐ |
| 削減と復旧 | 使用しない機能・テスト・依存を削り、対象の再起動・helper復旧・上流復帰を実機で確認する |
| 1.1の継続運用 | 必要な配布・更新経路で4系統を運用でき、手動の後始末や過去の所有証明を常時要求しない |

全設定の長大な棚卸しが完了するまで実機投入を待たない。まず実際に変更する構成を確認して進め、残す依存と削る対象を作業に合わせて確定する。例示設定を現在の実設定と偽って削除判断しない。

完成は、対象4系統の必要な通信、設定への復元、import、必要な再起動・復旧、不要部分の削除が実際に成立したことで判断する。試験件数、文書量、coverage、監査完了率は完成の代わりにならない。性能や復旧時間の数値目標は、利用者の要求または実運用上の必要から定める。

1.1の必要動作と運用が成立したら、1.5・2.0のブランチと専用リポジトリを廃止する。必要な改善は1.1側に取り込み済みとし、旧版の維持・試験・互換対応を続けない。成功前の先行削除は行わない。

## 10 過去の要求から反映した点

| 過去の論点 | 1.1への反映 |
| --- | --- |
| 2.0での実機最優先と不要な防御的テストの禁止 | 禁止事項を新旧コードへ適用し、例外は事前説明と利用者の了承に限定 |
| any多用、無駄な再変換、複雑な呼出し方への批判 | 具体型、境界での変換、状態担当の整理、置換済み経路の削除 |
| 個別の例だけを直して全体に方針が及ばない問題 | 4系統に必要な全呼出経路へ同じ原則を適用。未使用部分は保存せず削除 |
| 1.5初期のHealth/PBR、YAMLコピー、判断と実行の整理 | 1.0の実装へ小さく適用し、実機確認を先送りしない |
| commitされず成果が消える、状況が分からない問題 | 小さなcommit・push、具体的な進捗、実行事実と未確認事項の明示 |
| 家庭用とCloud SAMの用途 | 4系統の実設定に必要なWAN・IPv6・BGP・transport・SAM・RR/leaf等の依存を保持 |
| apt/pkg、再起動・自動再適用 | 対象環境の配布と復旧を実用品の要件として残す |

RR/leaf自動登録、SAMの選択した/32の移動、必要な元送信元・宛先の保持、使用するcloud連携やEvent Federationは、実設定の依存として確認する。試験用の全構成を追加したり、未使用のproviderやOSを維持する理由にはしない。

過去の「未リリース製品なので互換を捨ててよい」は、未使用の試作形式を残さない原則として受け継ぐ。今回明示された4系統の1.0設定互換を壊す許可として流用しない。
