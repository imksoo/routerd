# Linux 管理経路の分離 VLAN 構成変更試験

## 結果

現行 Linux パッケージで、`ManagementAccess` の許可送信元を独立した PVE VLAN 3133 の実通信で確認しました。許可範囲を変更すると接続結果が変わり、元の厳格な構成を再適用すると許可・拒否が復旧しました。

## 実施条件

- 実行リビジョン: `883dacbd3df3f0725e07f2985ccfcf559089b3f4`
- パッケージ SHA-256: `cd763b1a1356053dd6e7400358119a0edfbf23c674a16a4fd07ff580d7de83ad`
- VM219 は `rd15-admin` の `198.18.17.1/24` で候補実行物を新規状態領域に起動しました。HTTP 応答先は `198.18.17.1:18081` です。
- 独立した VM220 は VLAN 3133 の `rd15-mgmt` へ `198.18.17.10/24` と `198.18.17.11/24` を設定しました。

## 観測

- `allowSourceCIDRs: ["198.18.17.10/32"]` の構成は候補バイナリで検証に成功しました。
- `198.18.17.10` からは HTTP 200 と `routerd-management-access` の応答を確認しました。
- `198.18.17.11` からは接続不能でした。最終確認時の `nftables` 規則カウンターは、許可が 1 パケット、拒否が 3 パケットです。
- 許可範囲を `198.18.17.0/24` へ変更して適用すると、`198.18.17.11` から同じ応答を HTTP 200 で取得しました。
- 元の `/32` 構成を検証・再適用すると、`198.18.17.10` は HTTP 200、`198.18.17.11` は再び接続不能となりました。
- 途中で空構成も適用しました。この構成では管理規則は消えましたが、既定の入力遮断により `198.18.17.11` は到達しませんでした。この観測は「管理制限なしなら接続可能」の根拠にはしません。

## 手順上の訂正と未確認範囲

試験開始時に、追加した ISO を VM219 が認識するための再起動と、アーカイブ展開先ディレクトリの作成が不足していました。候補サービス停止前に検出・訂正しました。

VM219 と VM220 の復旧、試験用 ISO とスナップショットの削除は、この記録の後に別途確認します。データ転送障害中の管理経路、既存接続、IPv6、SSH、複数管理インターフェース、通常の `systemd` サービス経路、FreeBSD、および製品全体の合格は対象外です。
