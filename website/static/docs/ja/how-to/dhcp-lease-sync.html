HA ルーターの DHCP リース同期

2 台の routerd ノードで DHCP の役割を共有し、active node の lease state を standby node に温存したい場合は DHCPv4ServerLeaseSync、 DHCPv6ServerLeaseSync、または DHCPv6PrefixDelegationLeaseSync を使います。 これらは active から standby への同期を想定しています。backup が古い lease を active へ書き戻さないよう、通常は VirtualAddress の role で実行を制限します。

完全な例は examples/dhcp-lease-sync-ha.yaml にあります。

永続化の既定値を使う

routerd は既定で dnsmasq server lease を platform state directory 配下に置きます。 DHCP resource には実装上の lease path を書かない構成にします。

- apiVersion: net.routerd.net/v1alpha1
  kind: DHCPv4Server
  metadata:
    name: lan-dhcpv4
  spec:
    interface: lan
    addressPool:
      start: 192.168.30.100
      end: 192.168.30.199

- apiVersion: net.routerd.net/v1alpha1
  kind: DHCPv6Server
  metadata:
    name: lan-dhcpv6
  spec:
    interface: lan
    mode: stateful
    addressPool:
      start: fd00:30::100
      end: fd00:30::1ff

sync resource は source kind から実際の file path を導出するため、設定に実装上の path を繰り返す必要はありません。

active node からだけ同期する

lease sync をローカルの VirtualAddress status で制限します。VIP role が master の間だけ同期します。

- apiVersion: net.routerd.net/v1alpha1
  kind: DHCPv4ServerLeaseSync
  metadata:
    name: lan-v4-leases
  spec:
    source:
      resource: DHCPv4Server/lan-dhcpv4
    interval: 30s
    targets:
      - name: standby
        host: routerd-standby.lan.example
        user: routerd
    when:
      state:
        VirtualAddress/lan-vip.role:
          equals: master

stateful DHCPv6 server では DHCPv6ServerLeaseSync に source.resource: DHCPv6Server/<name> を指定します。WAN 側の prefix delegation は DHCPv6PrefixDelegationLeaseSync に source.resource: DHCPv6PrefixDelegation/<name> を指定します。

- apiVersion: net.routerd.net/v1alpha1
  kind: DHCPv6PrefixDelegationLeaseSync
  metadata:
    name: wan-pd-lease
  spec:
    source:
      resource: DHCPv6PrefixDelegation/wan-pd
    targets:
      - name: standby
        host: routerd-standby.lan.example
        user: routerd
    when:
      state:
        VirtualAddress/lan-vip.role:
          equals: master

standby が昇格した時は、空の database ではなく、最後に同期された lease state から 開始できます。

SSH の前提

lease sync は SSH 越しの rsync を使います。リソースを有効にする前に、非対話 SSH を準備してください。

  • active node の routerd 実行ユーザー用に SSH key を作成または配置する。
  • standby node の target.user の authorized_keys に公開鍵を入れる。
  • target.host の known_hosts を事前に管理する。BatchMode=yes により対話的な host-key prompt は出せません。
  • target user が導出された同期先 directory を作成し、lease file を書けるようにする。

routerd は、target.sshOptions が同じ key を上書きしていない場合、次の SSH 既定値を付けます。

-o BatchMode=yes -o ConnectTimeout=10

また rsync --timeout=60 を付け、各 sync command を controller の context deadline 付きで実行します。SSH option は target.sshOptions、rsync timeout は target.options で上書きできます。

targets:
  - host: routerd-standby.lan.example
    user: routerd
    sshOptions:
      - -o
      - ConnectTimeout=5
    options:
      - --timeout=30

確認

routerctl validate -f examples/dhcp-lease-sync-ha.yaml --replace
routerctl plan -f examples/dhcp-lease-sync-ha.yaml --replace
routerctl describe VirtualAddress/lan-vip
routerctl describe DHCPv4ServerLeaseSync/lan-v4-leases

node が master ではない場合、routerd serve は spec.when によりこの resource を 除外します。master で lease file が存在する場合、status は Synced へ進みます。 lease file がまだ無い場合は、dnsmasq が作成するまで Pending のままです。

復旧した同期失敗の調査

3種類のリース同期では、既存のサービスログへ DHCP lease synchronization failed を記録します。 リソース、失敗理由、転送元ファイル、転送先、コマンド名、エラー、処理の出力を確認できます。 取得できた場合は、終了コードを exitCode に記録します。値が -1 の場合は通常の終了コードがありません。 時間切れは timedOut、キャンセルは canceled で区別します。設定の不備やファイル情報の取得失敗も記録します。

同期が復旧した後も、次のコマンドでサービスログを確認できます。

journalctl -u routerd.service --since '1 hour ago' --no-pager | grep 'DHCP lease synchronization'

診断用の文字列は、各項目の末尾4096バイト以内を保持し、有効なUTF-8を維持します。 切り詰めた項目には <field>Truncated=true を記録します。 完全なコマンド引数、SSHオプション、リースの内容を明示的に記録する処理は追加しません。 外部処理の診断出力にはパスや端末名が含まれ得るため、通常のログと同様にアクセスを管理してください。 同じ失敗が連続する場合は、最初の1件を記録します。詳細が変わった場合や復旧後の再発は再び記録します。 復旧時の記録は DHCP lease synchronization recovered です。 失敗ログは状態の保存より先に出力するため、状態の保存に失敗しても元の転送エラーを記録できます。

保存期間は既存のサービスログの設定に従います。新しいログファイル、常駐収集処理、状態変更イベントは追加しません。 復旧後の現在の状態は、従来どおり Synced です。同期間隔、再試行、時間制限、転送動作も維持します。 リース同期の失敗は相手機への状態コピーの問題であり、それだけでDHCP応答の失敗とは判断できません。

DHCPv4の固定割り当て保持情報は、SQLiteのデータベース本体と更新履歴（WAL）を同期します。 一時的な共有メモリー索引 -shm は同期対象から除外し、受信側でSQLiteが再作成します。 データベース本体や更新履歴の転送失敗は、引き続きエラーとして記録します。 このファイル転送は、同時更新中のデータベース全体を一時点の状態として複製する方式ではありません。
